하루 만에 게임 만들기

시작

교육 과정에서 채용박람회와 함께 AI 게임 제작 이벤트를 열었다. 출품작 중 10개를 뽑아 행사 당일 부스에서 방문객이 직접 해 보게 한다는 행사였다.

처음에는 관심이 없었다. 그런데 주변에서 하나둘 게임을 만드는 과정을 보니, 한 번 경험해 보는 것도 좋겠다는 생각이 들었다. 그때 마감까지 남은 시간은 하루였다. 하루 만에 게임 하나를 어디까지 만들 수 있을지 궁금해졌고, 그래서 응모했다.

과정은 Claude Code와 대화하며 진행했고, 논의와 수정이 생길 때마다 원인과 결과를 문서로 남겼다. 이 시리즈는 그 기록을 정리한 것이다. 개발은 아직 진행 중이라 다음 편은 작업이 끝나는 대로 이어서 쓴다.

편 내용
01 조건을 정하고, 방향을 탐구하고, 개발을 시작했다 (이 글)
02 가상 플레이어로 밸런스를 잡았다 (작성 예정)
03 방향키 커맨드에서 타이밍 원버튼으로 바꿨다 (작성 예정)
04 데모 플레이, 피버, 전투 연출로 손맛을 더했다 (작성 예정)
05 마감과 제출, 하루를 돌아보며 (작성 예정)

처음 정한 조건은 네 가지였다

요강을 자세히 보기 전에, 부스에서 돌릴 게임이라는 것만 생각하고 조건을 먼저 정했다.

조건 내용
플레이 시간 3~5분 이내
실행 환경 오프라인 + 웹. Netlify 정적 배포를 생각했다
랭킹 점수 순위, 게임을 꺼도 기록 유지. SQLite를 생각했다
닉네임 입력 가능

이 조건으로 기획서를 요청했다.

기획서를 달라고 했더니 게임 하나가 정해져 나왔다

처음 받은 결과물은 "NEON 180"이라는 회피 아케이드 기획서였다. 180초 동안 빛을 모으는 게임 하나를 정하고, 화면 목업부터 디렉토리 구조, DB 스키마, 일정까지 바로 구현할 수 있는 스펙으로 써 있었다.

완성도는 높았지만 원했던 것이 아니었다. 아직 어떤 게임을 만들지도 정하지 않았는데, 답이 하나로 정해져 있었다. 내가 원한 것은 바로 만들 스펙이 아니라 방향을 고르기 위한 탐구 자료였다. 그래서 다시 요청했다.

방향부터 펼쳐 놓았다

두 번째 문서는 장르, 이야기, 포지션을 선택지로 펼쳐 놓은 탐구 자료였다.

다룬 내용 요점
조건이 주는 힌트 짧은 플레이는 10초 안에 규칙을 이해해야 한다는 뜻이다. 로컬 랭킹은 기기 하나를 여럿이 쓰는 부스에 맞는다. 닉네임은 주인공 이름으로 쓸 수 있다
방향 축 6개 반사신경↔사고력, 실력↔운, 긴장↔편안, 게임성↔이야기, 혼자↔경쟁, 매판 동일↔랜덤
장르 후보 8개 회피 아케이드, 경영 러시, 타이핑·퀴즈, 원버튼 타이밍, 병합 퍼즐, 추리, 마이크로게임, 자원 배분
이야기 강도 L0(추상)부터 L4(누적 이야기)까지. 3분 게임은 L1~L3이 효율적이다
포지셔닝 페르소나 4개, 포지셔닝 맵, 톤·무드 6종

마지막에는 기준마다 가중치를 바꾸면 방향 6개의 적합도가 다시 계산되는 비교 도구를 넣었다. "실력 경쟁"을 중요하게 보는지, "누구나 쉽게"를 중요하게 보는지에 따라 순위가 바뀐다.

좋아하는 장르냐, 새로운 장르냐

행사 성격을 다시 생각했다. 취업 박람회 부스이고, 전체 출품작 중 10개만 뽑힌다. 그러면 게임은 두 관문을 넘어야 한다.

  • 심사에서는 다른 출품작과 달라 보여야 한다.
  • 현장 부스에서는 처음 보는 사람이 10초 안에 이해해야 한다.

완전히 익숙한 게임은 심사에서 묻히고, 완전히 새로운 게임은 현장에서 설명이 필요하다. 그래서 게임을 조작·규칙과 소재·맥락 두 축으로 나눠 봤다.

조작 익숙함 조작 신선함
소재 신선함 ① 추천. 아는 조작 + 행사 맞춤 소재 ② 고위험 고보상
소재 익숙함 ③ 레드오션 ④ 규칙 하나만 비틀기

결론은 선호 장르의 조작을 빌리고, 행사 맥락의 소재로 신선함을 만든다였다.

요강을 받아 보니 전제가 바뀌었다

여기까지 와서 공모 요강을 제대로 확인했다. 처음 정한 조건과 다른 점이 많았다.

요강 바뀐 점
마감 11/10(화) 17:00 남은 시간이 하루. 작업량이 큰 방향은 뺐다
인터넷 없이 Windows에서 실행 Netlify가 필요 없다. 더블클릭으로 열리는 HTML 파일 하나가 가장 안전하다
로컬 기록 유지 SQLite는 요구사항이 아니었다. 더블클릭 실행에서는 WASM 로딩이 막히기 쉬워 localStorage로 정했다
누구나 쉽고 빠르게 3~5분 대신 1~2분
ZIP + 설명서 게임 소개, 실행 방법, 조작 방법, 랭킹 확인 방법을 써야 한다
운영사 검토로 선정 실행이 안 되면 사실상 탈락. 실행 안정성이 가장 중요하다
1인 1개 2개 이상 내면 미제출 처리

처음 조건 4개 중 플레이 시간, 실행 환경, 저장 방식 3개가 바뀌었다. 그대로 갔다면 웹 배포와 DB를 붙이느라 하루를 썼을 것이다.

아이디어를 하나씩 던지며 좁혀 갔다

방향과 조건이 정해진 뒤에는 아이디어를 하나씩 꺼내고, 하루 안에 만들 수 있는지와 부스에 맞는지를 따지며 좁혔다.

순서 아이디어 판단 남은 것
1 도트 핵앤슬래시 보는 재미는 크지만 애니메이션과 타격감 작업이 하루 안에 빠듯하다 도트 그래픽
2 도트는 정적인 화면에만 쓰고 다른 장르로 애니메이션 비용이 사라진다. 교육 과정이 개발 직종이니 그걸 소재로 개발 소재
3 무작위 강화 중 하나를 고르는 운 + 선택 매판 다른 빌드가 나온다. 운이 랭킹을 망치지 않게 3장 중 선택, 확률 공개, 보정 장치를 둔다 강화 카드
4 스노우볼, 후반 역전 트랙 좋지만 이번 범위에서는 보류 백로그
5 공략형, 점수형, 목표 도달형 성취감(목표)과 랭킹(점수)을 둘 다 잡는 혼합형 목표 도달 + 점수 랭킹
6 목표까지를 레이어로 나누고 확정 카드 + 운 보너스 확정 보상이 바닥을, 운이 천장을 만든다. 확정 70 : 운 30 레이어 구조
7 타임어택, 레이어 클리어, 보스, 루트 선택 = 난이도, 운 보너스 다섯 요소를 루트 맵 하나로 묶었다 핵심 구조
8 타이핑 대신 방향키 커맨드 한/영 전환 문제가 없고, 누구나 할 수 있고, 구경하는 사람도 따라 볼 수 있다 방향키 커맨드
9 레이어 소재: 커리어 사다리 vs 프로젝트 공정 개발 맥락과 가장 가까운 프로젝트 공정 기획 → 개발 → 테스트 → 출시

가장 오래 고민한 것은 3번과 6번, 운을 얼마나 넣을지였다. 운이 없으면 매판 똑같아서 다시 할 이유가 줄고, 운이 크면 랭킹이 실력이 아니라 뽑기가 된다. 그래서 확정 카드가 점수의 바닥을 보장하고, 운은 위쪽만 열어 두는 쪽으로 정했다.

「릴리즈 러시」로 정했다

릴리즈 러시 (가칭) — 방향키 커맨드로 프로젝트 공정을 돌파하며, 층마다 "검증된 방식"과 "신기술 도입" 중 하나를 골라 제한 시간 안에 출시까지 가는 게임.

설계 당시에는 제한 시간 120초, 3층(기획·개발·테스트)과 보스(출시 D-Day), 확정 카드 10종, 특수 보상 4종, 룰렛과 보정 장치, 칭호 5단계로 잡았다. 층마다 안전한 "검증된 방식"과 위험하지만 보상이 큰 "신기술 도입" 중 하나를 고르면서, 플레이어가 스스로 난이도를 정한다.

배포 방식으로 Electron도 이야기했다. 브라우저마다 기록이 갈리는 문제를 없애고 프로그램처럼 보이는 장점이 있었다. 하지만 서명 없는 exe의 Windows 보안 경고, 백신 오탐, 80~100MB 용량, 추가 작업 시간이 걸렸다. HTML 게임을 먼저 완성하고 배포 방식은 나중에 정하기로 했다.

HTML 파일 하나로 개발을 시작했다

요강의 실행 조건이 기술 선택을 거의 다 정해 줬다.

요구 선택 이유
인터넷 없이 Windows에서 실행 외부 CDN, 웹폰트, 이미지 파일 없음 오프라인에서도 그대로 동작한다
압축 풀고 더블클릭 <script type="module">을 쓰지 않음 더블클릭(file://) 실행에서는 ES 모듈이 막힌다
기록 유지 localStorage SQLite(sql.js)는 WASM 로딩이 더블클릭 실행에서 막히기 쉽다
폰트 맑은 고딕 Windows에 기본으로 들어 있다

화면은 캔버스와 HTML을 섞었다. 도트 배경과 커맨드는 320×180 캔버스를 4배로 키워 그리고, 닉네임 입력, 카드, 룰렛, 랭킹처럼 글이 많은 화면은 HTML로 올렸다. 도트는 선명하게, 글자는 부드럽게 보이게 하려는 것이다.

설계서대로 첫 초안을 만들었다. 대기 화면(TOP 10) → 닉네임 → 시작 카드 → 루트 선택 → 층(방향키 커맨드) → 보상 카드 → 룰렛 → 보스 → 결과까지 한 판이 이어진다.

카드 선택 룰렛

그림 10. 시작 카드 선택(왼쪽)과 운 보너스 룰렛(오른쪽)

사람이 매번 직접 해 볼 수 없어서, 게임 안에 점검용 훅(window.__RR)을 넣었다. 시간을 빨리 감고, 키 입력을 보내고, 저장된 기록을 꺼내 볼 수 있다. 이걸로 실력이 다른 가상 플레이어를 돌려 확인했다.

  • 처음부터 결과 화면까지 끊기지 않고 진행됐다. 보스를 깨고 끝나는 경우와 시간 초과로 끝나는 경우 모두 확인했다.
  • 카드 효과, 10초 자동 선택, 창을 벗어나면 자동 일시정지가 동작했다.
  • 새로고침한 뒤에도 기록 5건과 마지막 닉네임이 남아 있었다. 콘솔 오류는 없었다.

남은 문제

  • 120초가 적당한지 모른다. 설계서의 수치는 직접 해 보기 전에 정한 추정값이다.
  • 가상 플레이어는 사람이 아니다. 빨간 화살표(반대 방향 입력) 앞에서도 느려지지 않아서, 위험 루트가 실제보다 쉬워 보일 수 있다.
  • 설계서와 구현이 벌써 갈라지기 시작했다. 설계서는 첫 버전 기준으로 두고, 바뀌는 내용은 원인과 결과를 개발 로그에 남기기로 했다.
  • 배포 방식을 아직 정하지 않았다. HTML만 낼지, Electron을 함께 낼지.

다음 글에서는 가상 플레이어로 수십 판을 돌려 보고, 120초를 60초로 줄인 과정을 정리한다.

기획 초반에는 답을 하나로 정하지 말고 선택지를 펼쳐 놓는다. 그리고 요강은 가장 먼저 읽는다. 처음 정한 조건 4개 중 3개가 요강을 보고 바뀌었다.
